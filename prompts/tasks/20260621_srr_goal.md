## 执行顺序

### Phase 0：安全和工作树隔离

- 记录当前branch、HEAD、git status和已有untracked files。
- 不覆盖任何旧checkpoint、prediction、metric、cache或submission。
- 所有新路径必须带task key、variant、fold和checkpoint。
- 若多个执行session并行修改代码，必须使用独立git worktree/branch并在合并前检查diff；禁止两个session直接同时改同一working tree。

### Phase 1：规格主线与Cine次线

优先启动 `20260621_srr_spec`。

若环境支持独立worktree/session，可同时启动 `20260621_cine_retrieval`；否则先完成SRR spec，再运行Cine task。Cine不得阻塞MyoPS主线。

`20260621_srr_spec` 必须实际抽取并读取Result4，不能依赖此前摘要。只有其result为`GO_FOLD0`时进入Phase 2。

### Phase 2：MyoPS fold0正式对照

执行 `20260621_srr_fold0`。

允许最多两个并行单GPU jobs，充分使用4-6小时有效训练预算，每个job总walltime不超过8小时。不要停在几个case/几个epoch smoke；one-batch和tiny-overfit只是进入正式fold0的gate。

只有decision为`GO_ABLATION`时进入Phase 3。其他decision按subtask要求停止、修复或保留conditional-only结论，禁止为了故事强行继续。

### Phase 3：关键消融

执行 `20260621_srr_ablation`。

允许最多三个并行单GPU jobs。只测试Result4正式故事的关键差异，不加入alignment、新backbone、新loss组合或外部repo。

只有model selection选出一个有效版本时进入Phase 4。

### Phase 4：条件式fold扩展

执行 `20260621_srr_expand`。

允许folds 1-4四个独立单GPU jobs并行，每个不超过8小时。config、code revision和训练预算必须冻结。若最终gate不是`LOCAL_GO`或`LOCAL_GO_WITH_CAVEAT`，停止，不生成submission。

### Phase 5：汇总

汇总MyoPS和Cine的全部结果，写overall final status。不得把Cine本地proxy解释成hosted metric，不得把一项metric提升掩盖另一项退化。

## 资源策略

- 计算资源充足时，应并行提交独立job，而不是人为缩成几个epoch。
- 每个job仍必须`<=08:00:00`，使用max-runtime、early stopping和best checkpoint。
- 默认`htzhulab`；只有队列明显长才按AGENTS fallback到`a100-gpu`、`volta-gpu`。
- 并行job必须使用独立输出和cache。
- 允许持续轮询Slurm状态、读取日志、在job完成后自动进入已授权的下一subtask。
- 不允许后台承诺后离开；每个阶段应把当前状态、job ID和结果写入对应result/progress。

## 硬性禁止

- 不要official validation submission、外部上传或upload-ready package。
- 不要使用外部训练数据、validation pseudo-label或新下载权重。
- 不要继续patch旧MyoPS-Net/U-MyoPS/CineMyoPS third-party主路径。
- 不要跳过Result4 architecture contract。
- 不要把no-T2 cases当edema hard negative。
- 不要跳过fold0 gate直接扩fold。
- 不要同时改变backbone、fusion、loss、alignment和postprocess导致无法归因。
- 不要以foreground mean或单一metric作为总体成功。
